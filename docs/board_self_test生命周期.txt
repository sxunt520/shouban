生命周期
这个文件的核心是一个“板载设备控制器/自检脚本”，入口在 board_self_test.c 的 app_main。它的生命期大致可以分成 5 个阶段：

1. 启动与硬件初始化
在 app_main 里，程序先做一轮硬件准备：

配置 RGB 状态灯
如果启用了显示屏，则初始化 LCD
如果启用了扬声器，初始化 I2S 声音输出并播放启动音
如果启用了麦克风，初始化 I2S 麦克风并执行 20 秒的麦克风自检
打印板载信息
读取 NVS 中保存的配置，如当前音量
这一步相当于“设备开机自检 + 载入持久化状态”。

2. Wi‑Fi 连接
然后进入 connect_wifi：

检查 Wi‑Fi SSID 是否配置
初始化 Wi‑Fi / netif / event loop
连接到指定 Wi‑Fi
等待 IP_EVENT_STA_GOT_IP 成功事件
连接成功后给 LED 一次绿色脉冲，表示网络已连上
如果连接失败，程序会持续闪烁蓝灯并进入死循环，表示“设备不可用”。

3. 获取设备会话与认证
在后台网络任务 figure_network_task 中，程序进入长期运行循环：

如果 access_token 为空，就调用 create_device_session
这个请求会带上 hardwareId 和 deviceSecret
成功后拿到 accessToken，并显示 pairing code
accessToken 会保存在内存中，后续 API 调用都用它做认证
这个阶段是“设备注册/鉴权”。

4. 心跳 + 拉取命令
之后每隔一段时间执行一次循环：

send_heartbeat：向后端发送心跳，带上 firmwareVersion 和 volume
后端返回：
pendingCommandCount
bound
如果返回 200/201，则再执行 fetch_commands
fetch_commands 会拉取设备命令列表，并遍历执行每条命令
命令处理逻辑里支持几种类型：

set_volume：更新音量并写入 NVS
sync_character：保存角色/人物绑定
speak_text：模拟说话
play_reminder：模拟提醒播放
如果命令没法立刻执行，就会标记为 deferred（延迟），直到外设就绪后再处理。

5. 命令确认与持续运行
对于每个已收到的命令：

先 post_device_event，记录事件
如果 execute 成功：
调用 acknowledge_command
记录 command_acknowledged
如果失败或延迟：
记录 command_deferred
整个程序不是一次性任务，而是一个长期驻留的守护循环：

启动
连网
登录/绑定
心跳
拉取命令
执行命令
持续循环
也就是说，这个文件的生命周期本质上是：
“板子开机自检 → Wi‑Fi 连接 → 设备认证 → 定时心跳/命令处理 → 长期在线守护”。

这类文件更像一个 IoT 设备控制器的“主循环”，而不是传统的一次性程序。它的结束条件通常是设备断电或看门狗重启，而不是自然退出。
